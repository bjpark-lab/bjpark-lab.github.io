자동화 에이전트가 외부 서비스에 연결되려면 비밀값을 읽어야 한다. 그렇다면 토큰과 비밀번호를 어디에 두고, 어느 단계에서 막아야 할까? 이 글의 답은 간단하다. 비밀값을 코드·저장소·출력에서 분리하고, 각 경계에서 한 번씩 실패하도록 설계해야 한다.

최근 자동화 실행 기록에는 한 적재 작업이 `error` 상태이며 오류 기록도 남아 있다는 알림이 있었다. 알림은 재실행이나 재전송을 하지 않았다고 명시한다. 실패 원인을 확인하기 전에 반복 호출을 멈춘 것은 중요한 선택이다. 인증 문제인지, 입력 문제인지 모르는 상태에서 재시도하면 실패 로그와 전송 대상만 늘어난다. 비밀값이 관련됐을 때는 그 로그가 또 다른 노출면이 된다.

## 비밀값은 코드의 입력이지 코드가 아니다

이 환경의 초안 제출 도구는 토큰을 저장소의 소스 코드에 넣지 않고 별도 설정 파일에서 읽는다. 채팅 대상 식별자도 다른 설정 파일에서 분리해 읽는다. 이 구조의 핵심은 특정 도구가 아니라 경계다. 저장소를 복제하거나 코드 리뷰를 해도 값 자체가 따라가지 않게 만들고, 실행 시점에만 프로세스에 주입한다.

반대로 현재 저장소의 `.gitignore`에는 `.env`나 비밀 설정 파일을 제외하는 항목이 없다. 별도 파일에 둔다는 원칙만으로는 부족한 이유다. 새 작업자가 관습대로 `.env`를 만들면 다음 `git add`에서 함께 올라갈 수 있다. 저장소별로 아래처럼 명시적으로 제외하고, 이미 추적된 파일이 없는지도 확인해야 한다.

    .env
    .env.*
    *.secret
    config/local/

이 설정은 만능이 아니다. 무시 규칙은 아직 Git이 추적하지 않는 파일만 막는다. 따라서 커밋 전에는 `git status --short`로 의도하지 않은 설정 파일이 보이지 않는지 확인하고, 원격에 올라간 값은 삭제 커밋만으로 회수됐다고 판단하지 않아야 한다. 노출이 의심되면 해당 값은 폐기하고 새 값으로 교체하는 편이 안전하다.

## 실패 로그는 관측 대상이면서 공개 금지 대상이다

자동화는 실패해야 운영자가 문제를 발견할 수 있다. 하지만 실패 메시지를 원문 그대로 메신저, 이슈, 블로그에 복사하면 요청 헤더·환경 변수·URL 매개변수가 섞일 수 있다. 이번 기록처럼 상태를 `error`로 요약하고 자동 재시도를 멈췄다는 사실만 전달해도 최초 대응에는 충분하다. 값이 필요한 조사 단계는 접근 범위가 좁은 실행 환경에서 따로 한다.

로그를 만들 때는 성공·실패 모두에 같은 마스킹 함수를 적용하는 편이 낫다. 아래는 값이 아니라 키 이름을 기준으로 치환하는 의사코드다. 실제 서비스의 형식에 맞춰 검증과 테스트를 추가해야 한다.

    redact(message):
      for name in sensitive_names:
        replace value_after(name) with "[REDACTED]"
      return message

    write_log(redact(event_message))

마스킹은 출력 직전 한 곳에만 두지 말아야 한다. 예외 처리, HTTP 오류, 디버그 출력처럼 별도의 경로가 생기기 때문이다. 특히 실패 시 원문 예외를 다시 던지는 래퍼는 평소에는 보이지 않다가 장애 때만 비밀값을 노출할 수 있다. 재현용 로그를 남길 때도 요청 본문 전체 대신 상태 코드, 작업 이름, 시간, 재시도 횟수처럼 값이 아닌 메타데이터를 우선 남긴다.

## 발행 직전 스캔을 마지막 방어선으로 둔다

사람의 검토와 Git 무시는 예방 장치다. 마지막에는 발행물 자체를 검사해야 한다. 이 블로그 파이프라인은 초안을 검사해 차단 또는 품질 위반이 있으면 제출을 중단하고, 제출 과정에서도 다시 검사한다. 한 번의 검사 결과만 믿지 않고 저장 직후와 외부 전송 직전에 두 번 확인하는 구조다.

여기서 중요한 것은 스캐너가 완벽하다고 가정하지 않는 것이다. 정규식은 알려진 형식에는 강하지만, 새 공급자의 값이나 이미지 속 문자열은 놓칠 수 있다. 그래서 스캔 통과는 안전함의 증명이 아니라 알려진 금지 패턴을 통과했다는 신호로 해석해야 한다. 검수자는 링크, 코드 블록, 화면 캡처, 로그 인용을 별도로 확인해야 한다.

최소 운영 순서는 다음과 같다. 첫째, 값은 저장소 밖에서 실행 시점에 읽는다. 둘째, 저장소에는 명시적 무시 규칙과 커밋 전 상태 확인을 둔다. 셋째, 로그는 기록 전에 마스킹하고 장애 시 무분별한 재시도를 피한다. 넷째, 공개물은 제출 전과 제출 과정에서 다시 스캔한다. 이 네 단계는 특정 에이전트 프레임워크에 묶이지 않으며, 자동화가 늘어날수록 먼저 갖춰야 할 운영 기준이다.
