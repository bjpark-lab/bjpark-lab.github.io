같은 적재 작업이 두 번 돌아도 데이터가 망가지지 않으려면 무엇을 먼저 설계해야 할까? 내 판단은 실행 완료 표시보다 **레코드의 동일성을 정의하는 키와 저장소의 제약을 먼저 설계하자**는 것이다. 이 글은 로컬 프로젝트의 코드와 테스트 구조를 읽고 정리한 설계 기록이다. 실제 데이터 파일이나 운영 DB는 읽지 않았으며, 실행 예시는 업무·금융 정보와 무관한 합성 이벤트만 사용한다.

## 완료 표시와 중복 방지는 서로 다른 문제다

블로그 도구의 `tools/blog/next_topic.py`는 사용한 주제 키를 JSON state 파일에 기록한다. `load_state()`로 읽고, 이미 사용한 키를 제외한 뒤, `save_state()`로 다시 저장하는 구조다. 다음 주제를 선택하는 데는 이해하기 쉬운 방식이다.

하지만 이를 데이터 적재의 유일한 중복 방어선으로 삼는 것은 추천하지 않는다. 다음은 실제 장애 보고가 아니라 코드 구조를 바탕으로 생각한 실패 시나리오다. DB 쓰기가 끝난 직후 완료 기록 전에 프로세스가 종료되면 같은 입력을 다시 시도할 수 있다. 반대로 완료부터 기록하면 저장이 실패한 입력을 끝난 것으로 취급할 수 있다. 파일 표시와 DB 변경이 따로 일어나므로 실행 순서를 바꾸는 것만으로 그 간격을 없애지는 못한다.

내가 두고 싶은 경계는 명확하다. state 파일은 진행 위치와 재시도 후보를 찾는 보조 장치로 쓰고, 동일 레코드를 다시 저장할 수 있는지는 DB에서 판정한다. 완료 기록이 없어도 재시도가 안전해야 한다. 모든 작업이 반드시 한 번만 실행된다는 약속이 아니라, 다시 실행해도 목표로 삼은 저장 상태가 달라지지 않게 만드는 약속이다.

## 해시보다 먼저 같은 레코드의 의미를 정한다

확인한 적재 코드의 `_dedupe_key()`는 날짜, 값, 정규화한 이름, 계정 이름, 순번 등을 문자열로 묶어 SHA-256 키를 만든다. 이름에는 `casefold().strip()`을 적용한다. 스키마의 `dedupe_key`는 `NOT NULL UNIQUE`이고 삽입 함수는 `INSERT OR IGNORE`를 사용한다. 애플리케이션에서 키를 계산하고 DB 제약으로 반복 삽입을 막는 조합이다.

중요한 것은 해시 함수의 이름이 아니라 입력 필드의 의미다. 같은 사건의 표현이 달라져도 같은 키가 나와야 하고, 실제로 다른 사건이면 다른 키가 나와야 한다. 안정적인 원본 이벤트 ID가 있다면 출처와 그 ID를 함께 쓰는 방식을 먼저 검토하겠다. ID가 없다면 업무상 식별 필드와 정규화 규칙을 명시해야 한다. 문자열을 구분자로 이어 붙일 때는 필드 안에 같은 구분자가 들어오는 경우도 검토할 필요가 있다.

현재 코드에는 주의할 조건도 있다. 파서는 날짜별 등장 순번을 증가시키며 그 순번이 중복 키에 포함된다. 동일 입력의 동일 순서 재실행과, 일부 행이 추가되거나 순서가 달라진 내보내기 재실행은 같은 문제가 아니다. 같은 날짜의 행 구성이 바뀌면 순번도 바뀔 수 있다. 기존 테스트를 근거로 모든 내보내기 변형까지 안전하다고 주장할 수는 없다.

순번을 무조건 빼는 것도 해법은 아니다. 다른 필드가 같은 사건이 실제로 반복되면 서로 다른 레코드를 합쳐 버릴 수 있다. 키 설계는 누락 위험과 중복 위험을 함께 비교하는 판단이다. 이번 작업에서 해당 프로젝트의 키를 수정하거나 대체안을 검증한 것은 아니다.

## unique 제약은 저장을 지키고 state는 진행을 기억한다

state 파일은 처리한 파일 목록이나 마지막 확인 위치를 표현하기 편하다. 반면 읽기와 다시 쓰기 사이에 다른 실행이 끼어드는 경우를 다루려면 별도 동시성 설계가 필요하다. 현재 JSON 저장 함수에는 잠금이나 DB와 묶이는 트랜잭션이 보이지 않는다. 따라서 그 파일만으로 동시 실행에 안전하다고 가정하지 않는다.

DB unique 제약은 레코드 단위의 동일성 규칙을 저장소에 둔다. 그러나 그 규칙이 잘못되면 DB는 잘못된 동일성을 충실히 강제할 뿐이다. 중복 입력을 무시할지 기존 값을 갱신할지도 별도의 정책이다. 변경되지 않는 이벤트라면 무시가 맞을 수 있지만, 정정된 원본을 반영해야 한다면 갱신할 필드를 정해야 한다.

확인한 서비스는 레코드 삽입과 여러 스냅샷 저장 함수를 차례로 호출하고, 각 저장 함수는 자기 연결을 연다. 따라서 레코드 삽입의 멱등성과 전체 적재의 일괄 성공은 구분해야 한다. 일부 단계만 완료된 뒤 재실행하는 상황까지 테스트해야 한다는 것이 내 설계 제안이다. 후속 알림이나 외부 요청의 중복까지 레코드 제약이 해결해 주는 것도 아니다.

## 재실행 테스트는 행 수뿐 아니라 내용을 비교한다

기존 `tests/test_store.py`의 중복 키 제약 테스트와 동일 레코드 재삽입 테스트를 선택해 실제로 실행했다. 결과는 선택한 테스트 2개 통과였다. 재삽입 테스트는 첫 삽입과 두 번째 삽입의 반환값, 최종 행 수를 확인한다. 해당 입력의 반복 저장을 확인한 결과이지, 동시 실행이나 파서의 입력 순서 변경을 확인한 결과는 아니다.

다음은 독립적인 축소 예시다. Python 표준 라이브러리만 사용하며 메모리 DB에 합성 이벤트를 저장한다. 프로젝트 적재 함수의 복사본이 아니라 중복 무시 정책의 실행 가능한 예시다. 충돌 대상을 명시해 어떤 중복을 무시할지 드러냈다.

```python
import sqlite3

with sqlite3.connect(":memory:") as db:
    db.execute("CREATE TABLE events (source TEXT NOT NULL, event_id TEXT NOT NULL, payload TEXT NOT NULL, UNIQUE(source, event_id))")
    sql = "INSERT INTO events VALUES (?, ?, ?) ON CONFLICT(source, event_id) DO NOTHING"
    records = [("demo", "event-a", "ready"),
               ("demo", "event-b", "done")]
    db.executemany(sql, records)
    before = db.execute("SELECT * FROM events ORDER BY event_id").fetchall()
    db.executemany(sql, records)
    after = db.execute("SELECT * FROM events ORDER BY event_id").fetchall()
    assert before == after
    assert len(after) == 2
    print("replay: unchanged, rows=2")
```

이 코드를 실행해 `replay: unchanged, rows=2`를 확인했다. 여기서는 행 수와 행 내용이 모두 유지되는지를 검사한다. 운영용 테스트에는 같은 ID에 다른 내용이 온 경우, 입력 순서 변경, 일부 저장 뒤 실패, 실패 후 재시작도 추가하겠다. 각각 무시·갱신·오류 중 무엇을 기대하는지 먼저 적어야 테스트가 설계 계약이 된다.

결론은 state 파일을 없애자는 것이 아니다. 진행 기록이 정확해야만 데이터가 안전한 구조에서, 진행 기록이 유실돼도 저장소가 같은 입력의 재시도를 받아낼 수 있는 구조로 책임을 옮기자는 것이다. 다만 안전성의 범위는 키가 정의하는 동일성과 실제로 실행한 테스트까지만 말해야 한다.

## 확인한 근거와 범위

- 블로그 도구: `tools/blog/next_topic.py`의 state 읽기·쓰기와 주제 제외 로직.
- 로컬 적재 프로젝트: `ingest/base.py`, `ingest/banksalad.py`, `db/store.py`, `db/schema.sql`, `services/import_service.py`의 자료형·키 생성·제약·호출 경계.
- 테스트: `tests/test_store.py`의 `test_transactions_dedupe_key_is_unique`, `test_insert_transactions_is_idempotent_and_creates_payment_account` 선택 실행.

브리프에 지정 소스가 없어 위 코드 경로에서 근거를 수집했다. 소스의 식별자와 구조만 근거로 삼았으며 원본 데이터 값, 실제 계정, 보유 항목, 개인 금융 수치는 예시에서 제외했다. 순서 변경과 중간 실패에 관한 항목은 이번 실행의 검증 결과가 아니라 다음 검증을 위한 제안이다.
