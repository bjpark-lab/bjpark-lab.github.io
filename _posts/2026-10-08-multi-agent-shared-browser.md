동일한 로그인 세션의 브라우저를 여러 에이전트가 쓰면 무엇이 충돌할까? 이 글의 답은 연결 자체보다 **탭 상태에 대한 가정과 작업 소유권**이 먼저 충돌한다는 것이다. 읽기는 병렬화하되 같은 탭을 바꾸거나 같은 요청을 보내는 구간은 직렬화하는 편이 안전하다. 근거는 직접 읽은 로컬 운영 지침과 공식 문서다. 이번 집필에서 실제 브라우저 충돌을 새로 재현한 것은 아니며 기록된 운영 문제와 최소 실행 예제를 구분한다.

## 탭 목록은 매번 확인할 상태다

Windows·WSL 브라우저 운영 지침에는 활성 탭에 무조건 연결하지 말고 먼저 목록을 읽은 뒤 대상의 정확한 식별자로 연결하라는 규칙이 있다. 연결 후에도 제목과 URL을 확인하도록 되어 있다. 창의 포커스와 작업 대상이 같다고 전제하지 않기 위한 로컬 운영 규칙이지 모든 제품의 보편적인 결함이라는 뜻은 아니다.

공유 환경에서는 이전 에이전트가 열어 둔 탭에 이미 필요한 결과가 있을 수 있다. 반대로 목록을 읽고 연결하는 사이에 다른 작업자가 탭을 이동시켰을 수도 있다. 오래된 제목만 믿고 버튼을 누르는 설계는 대상 검증을 건너뛴다. 이는 운영 규칙에서 도출한 실패 시나리오이며 실제 사고 횟수를 측정했다는 주장은 아니다.

권하는 순서는 목록 조회, 대상 식별자 선택, 연결 후 URL·제목 확인, 쓰기 직전 재확인이다. 대상이 사라졌거나 예상 페이지와 다르면 멈춘다. 비슷한 제목의 다른 탭을 임의로 대신 선택하지 않는다. 기존 탭을 재사용한다는 규칙 역시 무관한 사용자의 탭을 이동시켜도 된다는 허가가 아니다.

## 재시도 전에 기존 결과부터 읽는다

같은 지침에는 입력창 채우기 호출이 실패해도 실제 텍스트가 들어가 있을 수 있으므로 재시도 전에 내용을 읽으라는 주의가 있다. 전송 전에는 불확실한 상태를 기록하고 이후 사용자 메시지가 생겼는지 확인하도록 되어 있다. 확인한 것은 지침의 내용이지 특정 서비스에서 오늘 같은 오류가 발생했다는 사실은 아니다.

이를 공유 브라우저에 적용하면 완료 여부를 에이전트의 기억만으로 판단할 수 없다. 다른 작업자가 이미 전송한 요청을 다시 보내면 중복 작업이 된다. 전송 직전 메시지 식별자 목록을 기준점으로 저장하고 이후 추가된 메시지를 확인하는 방식이 유용하다. 응답이 보이지 않는다고 새 요청을 만들지 않고 기존 사용자 메시지와 입력창부터 확인하는 것이 핵심이다.

작업 키에는 탭 번호만 넣기보다 목적을 넣는 편을 권한다. 같은 문서의 요약이라는 작업 키에 담당 에이전트, 대상 식별자, 진행 단계, 검증 결과를 함께 기록할 수 있다. 대상 식별자는 연결 대상을 찾는 값이고 작업 키는 중복 실행을 막는 값이다. 역할을 분리해야 탭이 바뀌어도 완료된 작업을 다시 시작하지 않는다.

## 최소 예제: 확인과 점유를 한 구간으로 묶기

다음은 Linux·WSL용 Python 표준 라이브러리 예제다. 브라우저를 제어하지 않고 같은 작업 키의 중복 점유를 막는 부분만 검증한다. 임시 디렉터리는 실행 환경의 TMPDIR 아래에 만들며 실제 프로젝트 데이터나 로그인 정보를 읽지 않는다.

```python
import fcntl
import json
import os
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(dir=os.environ["TMPDIR"]) as directory:
    root = Path(directory)
    state = root / "claims.json"
    lock = root / "claims.lock"

    def claim(key, owner):
        with lock.open("a+") as handle:
            fcntl.flock(handle, fcntl.LOCK_EX)
            claims = json.loads(state.read_text()) if state.exists() else {}
            if key in claims:
                return False
            claims[key] = owner
            state.write_text(json.dumps(claims))
            return True

    first = claim("document-summary", "agent-a")
    second = claim("document-summary", "agent-b")
    assert first is True and second is False
    print(first, second)
```

이 코드를 실행한 실제 출력은 `True False`였다. 확인 범위는 같은 키의 순차 점유 요청에서 뒤의 요청이 거부되는지 여부다. 실제 병렬 브라우저 조작이나 네트워크 전송의 멱등성을 검증하지는 않는다. 상태 확인과 점유 기록을 동일한 잠금 구간에 넣는 설계는 코드에서 확인할 수 있다.

이 예제를 그대로 운영 시스템으로 쓰지는 않는다. 점유 후 프로세스가 종료하면 작업 키가 남고 파일 쓰기 중 장애에 대한 복구도 없다. 실제 도입 시에는 점유 만료, 상태 파일의 안전한 교체, 실패한 소유권 회수가 필요하다. 모든 에이전트가 같은 규칙을 지켜야 한다는 한계도 있다. 잠금을 무시하는 다른 작업자까지 이 파일이 통제하지는 못한다.

## CDP 연결은 협업 스케줄러가 아니다

Playwright 공식 문서에서 connectOverCDP는 기존 브라우저에 Chrome DevTools Protocol로 연결하는 기능이며 Chromium 계열만 지원한다. 자체 프로토콜 연결보다 충실도가 낮아 고급 기능에 문제가 있으면 자체 프로토콜 연결을 고려하라고 설명한다. 연결만 확보하면 모든 자동화 기능이 동일하게 동작한다고 볼 수 없다는 제약이다. 출처: [Playwright 공식 문서 원본](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-browsertype.md).

Chrome 공식 안내는 Chrome 136부터 기본 데이터 디렉터리에 대한 원격 디버깅 포트·파이프 스위치를 그대로 인정하지 않으며 비표준 데이터 디렉터리를 함께 지정하도록 변경했다고 설명한다. 해당 명령행 스위치의 제약만 다루며 다른 연결 방식까지 불가능하다고 확대 해석하지 않는다. 출처: [Chrome 원격 디버깅 변경 안내](https://developer.chrome.com/blog/remote-debugging-port).

내 판단은 연결 방식과 협업 제어를 분리하자는 것이다. CDP로 페이지에 도달할 수 있다는 사실은 그 탭을 독점한다는 뜻이 아니다. 페이지 이동·입력창 변경·전송은 작업 키와 대상 탭을 확인한 담당자만 수행하도록 운영 규칙을 두는 편이 낫다.

## 완료는 호출 성공이 아니라 결과 확인이다

성공 조건을 호출이 오류 없이 끝났다는 사실로 잡으면 재시도와 중복 전송을 구분하기 어렵다. 권하는 완료 조건은 정확한 대상에서 요청이 확인되고 새 결과가 나타나며 결과가 작업 키에 연결되어 저장되는 것이다. 중간 단계가 불확실하면 완료도 실패도 단정하지 않고 확인 대기 상태로 남긴다.

로컬 근거는 브라우저 대상 선택·전송 확인·재개 규칙과 공유 작업 공간의 독립 검증 지침이다. 개인 대화 내용, 실제 입력값, 계정 정보는 사용하지 않았다. 병렬 에이전트의 장점은 더 많은 클릭을 동시에 만드는 데 있지 않다. 이미 끝난 작업을 반복하지 않으면서 서로의 상태를 덮어쓰지 않는 구조를 만드는 데 있다는 것이 이번 설계 판단이다.
